## Part B — Three cascading bugs in `scripts/class_ops.py`

### Bug #1 — `socket_connect_fail` on every subcommand (line 67)

**What was tried:** ran `class_ops.py derive .MaterialFlow.Station
.UserObjects TestStation`; envelope returned `error: "socket_connect_fail"`.

**Server reply (via the dispatcher's stderr-trace):** the underlying
`subprocess.run([sys.executable, SIMTALK_SEND, "--timeout", "30", code], …)`
call failed with exit 2 because `simtalk_send.py` rejected the unknown
positional arg `--timeout` (the timeout is a top-level option, not a
positional; the subcommand `run` was missing).

**Root cause:** the dispatcher passed the SimTalk code as the first
positional after `--timeout`, skipping the required `run` subcommand:

```python
# BEFORE — broken
proc = subprocess.run(
    [sys.executable, SIMTALK_SEND, "--timeout", str(int(timeout)), code],
    ...
)

# AFTER — fixed
proc = subprocess.run(
    [sys.executable, SIMTALK_SEND, "--timeout", str(int(timeout)), "run", code],
    ...
)
```

The `simtalk_send.py` CLI shape is:

```
simtalk_send.py [-h] [--host HOST] [--port PORT] [--timeout TIMEOUT]
                {ping,syntax,run,readlog} …
```

Top-level options, then subcommand, then positional. The original
dispatcher had been hand-written without the `run` subcommand.

### Bug #2 — `no_marker_block_in_log` after Bug #1 fix

**What was tried:** retried after Bug #1 fix; envelope returned
`error: "no_marker_block_in_log"`.

**Server reply:** `simtalk_run` succeeded (`result: "success"`) with
**empty** `log` field. Quirk #6 (v15+ regression — documented in
`local-simtalk-execution/references/lifelines.md` §5 and team memory
`simtalk-run-soft-failure-design`): `simtalk_run.log` no longer carries the
`print` output. The output is only retrievable via a follow-up
`simtalk_send.py readlog`.

**Root cause:** the dispatcher parsed `data` and the `log` field of the
single `simtalk_run` reply. After v15 that field is empty, so the
`###CLASS_OP### … ###CLASS_OP_END###` block the snippet wrote is never
visible to the parser.

**Fix:** added a readlog recovery pass right after every `simtalk_run`. On
v15+ `simtalk_send.py readlog` returns exit code **20**
(`readlog_unreliable_warning`); exit 20 still ships the log content on
stdout, so it is treated as success:

```python
rl_proc = subprocess.run(
    [sys.executable, SIMTALK_SEND, "readlog"],
    capture_output=True, text=True, timeout=20.0,
)
if rl_proc.returncode not in (0, 20):
    envelope["error"] = "readlog_fetch_failed"
    envelope["raw_reply_tail"] = (rl_proc.stdout or "")[-400:]
    return envelope

try:
    rl_resp = json.loads(rl_proc.stdout)
except json.JSONDecodeError:
    envelope["error"] = "readlog_not_json"
    envelope["raw_reply_tail"] = (rl_proc.stdout or "")[-400:]
    return envelope

log_text = rl_resp.get("log", "") or ""
data, err = parse_marker_block(log_text)
envelope["log_tail"] = log_text[-400:]
```

### Bug #3 — `Unknown identifier 'numMethods'` runtime exception

**What was tried:** `class_ops.py inspect .MaterialFlow.Station` after Bug
#1 and Bug #2 were fixed; envelope returned `error: "runtime"`.

**Server reply:** `simtalk_run` returned `result: "success"` with
`log: "code execute failed. error msg:Unknown identifier 'numMethods'…"`.
This is Quirk #7 (soft failure) — `result` is success but the SimTalk code
raised a runtime exception.

**Root cause:** `snippet_inspect` emitted `print "NUMMETHODS:" +
to_str(o.numMethods)`. There is no `numMethods` attribute on Plant
Simulation objects — the canonical read-only count attributes are
`NumAttr` and `NumChildren` only (per
`01-plantsimulation-knowledge/01-plant-simulation-help/objects/common-read-only-attributes/common-read-only-attributes.md`).

**Fix:** rewrote `snippet_inspect` to use the canonical names:

```python
def snippet_inspect(path: str) -> str:
    e = esc_str(path)
    return (
        snippet_resolve(path, "o")
        + T_HEADER
        + 'print "PATH:" + obj_to_str(o)\n'
        + 'print "NAME:" + o.Name\n'
        + 'print "TYPE:" + o.InternalClassType\n'
        + 'print "ORIGIN:" + obj_to_str(o.Origin)\n'
        + 'print "ORIGINROOT:" + obj_to_str(o.OriginRoot)\n'
        + 'print "CLASS:" + obj_to_str(o.Class)\n'
        + 'print "NUMATTRIBUTES:" + to_str(o.NumAttr)\n'
        + 'print "NUMCHILDREN:" + to_str(o.NumChildren)\n'
        + T_FOOTER
    )
```

The `numMethods` line was deleted entirely (the attribute does not exist).

## Part C — "Create a Station instance in `.Models.Model`" probe

### Scope clarification

The user's request "create a Station object in `.Models.Model`" is
**outside the scope of `local-simtalk-class-management`** — the skill
manages **classes** in the Class Library. Inserting an **instance** of a
class into a Frame is instance-side work (per the SKILL.md "Limitations"
section: *"No instance manipulation. … `class.create`, `instance.deleteObject`
… is out of scope; use `local-simtalk-execution` directly with bespoke
SimTalk for instance-side work."*).

The pre-flight `list .Models` step (via the fixed `class_ops.py`) confirmed
that `.Models.Model` is a **Frame**, not a Folder — `InternalClassType =
"Frame"`. So the user wants a Station **instance** placed inside the Frame.

The first attempt was via raw SimTalk through `simtalk_send.py run`:

```simtalk
var cls: object := str_to_obj(".MaterialFlow.Station")
var frame: object := str_to_obj(".Models.Model")
var inst: object := cls.create(frame)
```

**Server reply:** `code execute failed. error msg:Unknown identifier
'create'…`

### Probe — does Station have a `create` method?

```simtalk
var cls: object := str_to_obj(".MaterialFlow.Station")
var inst: object := cls.create
```

**Server reply:** same `Unknown identifier 'create'` — confirms `create`
is **not** defined on the Station class.

The Plant Simulation Help (`step-by-step/…/conveyor-track-agv-battery.md`
and `pick-place-robot-scenarios.md`) shows `<Class>.create(parent)` is
documented **only on MU classes** (Material Units: `Transporter`,
`Container`, `Box`, `Part`, `MainPartA`, `MainPartB`, …). Stations /
Conveyors / Sources / Drains / Buffers / etc. do **not** expose `create`.

### Probe — does path-navigation `.Models.Model.Station` auto-create?

```simtalk
var probe1: object := .Models.Model.Station
```

**Server reply:** `code execute failed. error msg:Unknown identifier
'Station'…`. Path resolution fails because `.Models.Model.Station` is not
a known path — Plant Simulation does not fall back to auto-creating an
instance from a Class Library class of the same name when the path is
absent.

### Probe — Frame's available methods

`common-methods.md` lists Frame's methods as `getHTMLCode`, `node`,
`pasteClipboard`, `statistics` (plus the inherited common methods like
`moveToFolder`, `setName`, `deleteObject`, `replace`, …). There is **no
`create`, `append`, `insert`, or `insertChild`** method on Frame.

### Probe — what does `.Models.Model` currently contain?

```simtalk
var p: object := str_to_obj(".Models.Model")
print p.NumChildren   -- → 0
```

**Server reply:** `FRAME_NUMCHILDREN:0` — the Frame is empty.

### Conclusion

Plant Simulation's public SimTalk API does **not** expose any method to
programmatically create a non-MU instance of a class. Material-flow objects
(Station, Conveyor, Source, Drain, Buffer, AssemblyStation, …) can only
be inserted into a Frame by:

1. **GUI drag-drop** from the Class Library toolbox onto the Frame window.
2. **Design-time static definition** in the model file.
3. (Windows only) **OLE/COM automation** — outside the scope of this TCP
   skill.

The `local-simtalk-class-management` skill (after the three fixes above) is
correctly limited to the Class Library; no additional instance-side ops
need to be added there.

> **Note:** this conclusion was **superseded by Part D** below —
> `<Class>.duplicate(parent, name)` CAN create non-MU objects, just not
> as instances inside a Frame.

## Part E — Folder vs Frame destinations (definitive test)

The user's challenge: my Part D conclusion that "Frame-destination
duplicate produces a class, not an instance" was wrong. The user
noted (correctly) that "anything created in a Frame is a runtime
instance; only things created in a Folder are classes". I
re-investigated.

### Re-reading `common-methods.md` §2 (general methods index)

```text
### derive [SimTalk]   (line 129)
Derives the object in the Class Library, i.e. creates a subclass
that inherits from it. Changes are applied immediately.

### duplicate [SimTalk]   (line 153)
Copies the object in the Class Library and creates a new class.
Inheritance relations to the original are cut.
```

**Key nuance I missed:** the `duplicate` docs example (line 161-167)
shows `.MaterialFlow.Conveyor.duplicate(.Models.Model, "MyConveyor")`
followed by `MyConveyor.setPosition := [100, 100]` — `setPosition` is
an **instance-only** operation (per §3 *Object Icons*, line 411-415:
"Sets the icon position of `<Path>` in the Frame (pixel coordinates)").
So `setPosition` only works on objects placed **in** a Frame.

The docs' wording "creates a new class" is misleading; `duplicate`
behaves **conditionally** based on the destination type.

| # | Quirk | Status |
|---|---|---|
| Q-B7 | `<Class>.duplicate(parent, name)` behaviour **depends on `parent`'s type**: Folder destination → new top-level class (Origin=VOID, Class=VOID, inheritance cut); Frame destination → instance (Origin/Class point to the original, inheritance preserved). | Q-B10 | `setPosition` is a **method call** `setPosition(X:integer, Y:integer[, CallMoveInFrameControl:boolean:=true])`, not an LVALUE attribute — `<obj>.setPosition := [x, y]` is a compile/runtime error. The `[100, 100]` array notation in `common-methods.md` is misleading. | **NEW** — API gotcha. |

### Corrected summary of `duplicate` semantics

| Destination type | Result | Origin/Class | Inheritance | When to use |
|---|---|---|---|---|
| **Folder** | New class in class library | VOID/VOID | Cut (no parent) | Add a brand-new class to the Class Library, e.g. `.MaterialFlow.MySpecialStation` |
| **Frame**  | Instance of the source class | Origin/Class point to source | Preserved | Place a runtime instance in a Frame for the simulation to use |

`derive` differs: it **always** creates a class (subclass) that
**inherits from** the source, regardless of destination type. Use
`derive` when you want a child class that maintains inheritance;
use `duplicate(Frame, …)` when you want a runtime instance;
use `duplicate(Folder, …)` when you want a standalone copy.

## Part F — `derive` vs `duplicate` (full matrix)

The user asked: when creating a class in a Folder, did I use `derive`
or `duplicate`? My answer: I had used `duplicate` in Part E, which
produces a **standalone class** (inheritance cut, Origin=VOID). For a
**subclass** (inheritance preserved), `derive` is the right choice.
This part documents the full matrix.

### Probe (`derive_vs_duplicate.snippet`)

```simtalk
-- A) derive to Folder
var d1 := .MaterialFlow.Station.derive(.Models, "DerivedStation")
-- B) derive with no args (default destination = next to source)
var d2 := .MaterialFlow.Station.derive
-- C) derive to Frame
var d3 := .MaterialFlow.Station.derive(.Models.Model, "DerivedInFrame")
```

### Server reply

### Full matrix

| Method | Destination | Result | Origin | Class | Inheritance | Use when |
|---|---|---|---|---|---|---|
| `derive` (no args) | next to source | Class | source | VOID | **preserved** | Quick subclass next to source |
| `derive(folder, name)` | Folder | Class | source | VOID | **preserved** | Add a true subclass to a folder |
| `derive(frame, name)` | Frame | Instance | source | source | preserved | (uncommon — same as `duplicate(frame)`) |
| `duplicate(folder, name)` | Folder | Class | VOID | VOID | **cut** | Standalone copy in class library |
| `duplicate(frame, name)` | Frame | Instance | source | source | preserved | Place a runtime instance in a Frame |

### Decision rule

- Want a **subclass** (can override parent attributes / methods) → **`derive`**
- Want a **standalone class** (no parent, fully independent) → **`duplicate(folder, ...)`**
- Want a **runtime instance** (placed in Frame, can be processed by simulation) → **`duplicate(frame, ...)`** (or `derive(frame, ...)`, equivalent)
- The class-vs-instance test (Origin/Class pattern from Q-B9) is **invariant** across all 5 cases: both VOID = class, both non-VOID = instance.

### Updated quirk table

| # | Quirk | Status |
|---|---|---|
| Q-B11 | `derive` and `duplicate` to the **same destination type** produce different kinds of classes: `derive` → subclass (Origin = source, can override); `duplicate(folder, ...)` → standalone class (Origin = VOID, no parent). The two are NOT interchangeable when the goal is "add a class to the class library". | **NEW** — important distinction for `class_ops.py derive` and `class_ops.py duplicate` subcommands. |
| Q-B12 | `derive` with no args places the new class **next to the source** in the class library tree, auto-suffixing the name with `_2` if the source name is already taken (e.g. `.MaterialFlow.Station.derive` → `.MaterialFlow.Station2`). | **NEW** — confirms the pre-flight rule warning about silent name-collision suffixes. |

### Final state — Part F

✅ **Decision rule established**: `derive` for subclasses (inheritance
preserved), `duplicate(folder, ...)` for standalone copies, and
`duplicate(frame, ...)` for runtime instances. The user was right to
ask — I had defaulted to `duplicate` in Part E, which produced a
**standalone** class (Origin=VOID). If the user's intent was "add a
class that relates to the source", `derive` is the correct choice.
